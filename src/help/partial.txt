wonderpress partial — reusable render primitives

A partial is a PHP class plus a view template: the unit of markup in a
Wonderpress theme. Once created it can be rendered two ways, from one source:

  from PHP        echo new \Wonderpress\Partials\Testimonial([ ... ]);
  in the editor   by also giving it a block — see `wonderpress block help`

A partial is not a Gutenberg block. A block is a thin wrapper over a partial.
Most partials have no client-side behavior. JS is opt-in, either at create
time or later — both produce the same Static Kit class:

  both at once        wonderpress partial create --name Hero --js
  add to an existing  wonderpress partial add-js Hero

The file is not auto-imported; wire it from the page JS entry that renders
the partial.

COMMANDS
  partial create           Create one (class, view, style, optionally JS + block)
  partial add-js [<Name>]  Scaffold a JS behavior class onto an existing
                           partial. With no name, pick from those that have a
                           view and no script yet.
  partial list             List every partial, and whether a block wraps it
  partial sync [<Name>]    Regenerate the class's generated region and
                           block.json from the manifest (after you edit
                           properties in JSON). Custom PHP is kept; see FENCES
  partial check-drift [<Name>]
                           Report each partial as clean, pending, or conflict
                           against its last sync (see SYNC STATES; use in CI)
  partial remove [<Name>]  Delete a partial and everything it owns. With no
                           name, pick from what the theme has.
  partial install-manifest <slug>
                           Copy a core primitive manifest (e.g. link) into
                           .wonderpress/manifest/partials/

CREATE OPTIONS
  <Class_Name>             The name, positionally — `partial create Hero`.
                           --name <Class_Name> does the same thing.
                           With no name at all, the wizard runs, and any flags
                           you passed pre-answer its questions rather than being
                           asked again.
  --prop <name:type[:required]>
                           A property, repeatable. Types: string, boolean,
                           image, link, repeater, array, object
  --sub <parent:name:type[:required]>
                           A sub-field of a repeater property (repeatable)
  --block                  Also expose it in the editor (off by default —
                           most partials are compositional, not blocks)
  --js                     Also scaffold a JS behavior class (off by default)
  --acf                    Register an ACF field group from the manifest
                           (requires the manifest; locate it with template
                           composition or wonderpress_template_fields)
  --template-name <file>   Name the view template, e.g. my-view.php
  --no-template            Class only, no view template
  --no-style               Skip the SCSS stub
  --no-manifest            Skip the manifest (cannot be combined with --block
                           or --acf)
  --json <spec|@file>      Create from a JSON spec instead of flags
  --force                  Re-create an existing partial even when its
                           generated output was edited by hand since the last
                           sync (a conflict), or its class lost its markers
  --theme <name>           Target a theme by name, skipping the active lookup
  --format json            Machine-readable envelope (list, sync --dry-run,
                           check-drift)

  --block --no-manifest and --acf --no-manifest are refused. --js --no-template
  emits no behavior class. --block and --acf may be combined: the block uses
  Gutenberg attributes; the PHP caller uses ACF. Do not locate the ACF group
  on a page that also inserts the block.

SYNC OPTIONS
  --all                    Sync every partial manifest in the theme
  --slug <slug>            Partial slug (alternative to positional name)
  --dry-run                Print what would be written, without changing files
                           (JSON plans include classAction: create, update,
                           unchanged, migrate, force, or refuse)
  --properties-only        Update class + block.json only (skip render.php)
  --force                  Sync even a partial in conflict, overwriting hand
                           edits inside the fence and in block.json. Code
                           outside an intact fence is still kept. A class with
                           no or malformed markers is rewritten whole.

FENCES
  The partial class has one machine-owned region:

      // <wonderpress:generated>
      ...$acf_compatible, $partial_template, $properties...
      // </wonderpress:generated>

  Sync rewrites only that region, from the manifest. Everything else in the
  file is yours and is kept byte for byte: put custom methods inside the class
  below the closing marker. Editing inside the fence is a conflict (check-drift
  reports it, sync refuses it); change the manifest and sync instead.

  A class from before fences is upgraded on its next sync when it is still
  exactly what sync generated. If it was edited, sync refuses rather than lose
  your code: move the custom code aside, run sync with --force, then put it
  back below the closing marker. The class path comes from the manifest's
  artifacts.class; create, sync, and block create all keep it.

SYNC STATES
  Every sync (and create) records what it wrote in a lock beside the
  manifest, .wonderpress/manifest/partials/<slug>.lock.json. Commit it,
  and leave it alone: it is not a manifest. check-drift compares
  the manifest, the generated files, and that lock:

    clean      nothing changed since the last sync (prints nothing)
    pending    the manifest changed, a generated file is missing, or there
               is no lock yet. Sync is owed and safe.
    conflict   the generated region of the class, or block.json, was edited
               by hand since the last sync. Sync refuses it: move custom PHP
               below the closing marker (or put the change in the manifest,
               or revert it) in your editor, or run sync --force to overwrite.

  check-drift prints one line per partial that is not clean and exits 1 on a
  conflict or when generated files no longer match the manifest. A pending
  partial whose files still match (no lock yet) is reported but exits 0.
  sync --all skips partials it refuses (conflict, or a lock-less class with
  hand edits and no markers) with a warning and syncs the rest. Re-running
  partial create on a partial in conflict is refused the same way; add
  --force to regenerate it.
  --format json: data.partials[] of { slug, state, changes[] }, where each
  change is { artifact, region, kind, state, message }.

REMOVE OPTIONS
  --with-block             Also remove the block wrapping this partial.
                           Without it, remove refuses when a block exists.

EXAMPLES
  wonderpress partial create --name Testimonial --prop quote:string:required
  wonderpress partial create --name Hero --block --js
  wonderpress partial add-js Hero
  wonderpress partial create --name Testimonials --acf --prop items:repeater --sub items:quote:string:required
  wonderpress partial sync Scalar_Demo
  wonderpress partial sync --all
  wonderpress partial sync Hero --force
  wonderpress partial check-drift --all
  wonderpress partial create
      No flags runs the interactive wizard, which asks the same questions.
